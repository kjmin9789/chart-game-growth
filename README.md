# 차트게임 시드 매출 성장 기획

알파스퀘어 차트게임의 시드 매출을 높이기 위한 개인 비공개 기획 저장소다. 문제 정의부터 근거, 실험 선택, 역할별 태스크, 결과에 따른 다음 결정까지 연결한다.

현재 단계는 **기준 결제 집계 확보 및 구매 원인 진단**이다. 목표는 시드 매출이며, 임팩트가 크고 작업 규모가 작은 실험을 우선한다. GA·어드민 집계를 정리했고, 구매자의 플레이·잔액·부족 상황을 연결한 뒤 첫 실행 실험을 고른다.

## 기획에서 구현까지

1. 관찰한 현상과 원인 가설을 구분하고 근거를 남긴다.
2. 대상 사용자와 매출로 이어지는 경로를 정리해 작은 실험 하나를 고른다.
3. 실험안에 비교군, 측정 기간, 성공 기준과 보호 지표를 적는다.
4. 개발 전달이 필요한 요구사항은 `request/YYMMDD-태스크명.md`에 작성한다. [작성 규칙](TASK-WRITING.md)을 따른다.
5. 실제 코드 변경과 코드 PR은 알파스퀘어 조직의 해당 저장소에서 진행한다. 요구사항에 실제 이슈·PR 링크를 연결한다.
6. 배포 확인, 실험 결과, 다음 결정을 이 저장소에 기록한다.

기획 확정, 구현 완료, 운영 배포, 매출 개선 확인은 각각 다른 상태로 기록한다. 담당자와 일정은 합의 후 확정한다.

## 문제와 실험 및 태스크의 관계

**문제 → 후보안 비교 → 개별 실험 → 태스크 실행 → 결과와 다음 결정** 순서로 관리한다. 스프린트는 이 가운데 이번 기간에 진행할 작업을 모으는 실행 단위다.

- **문제:** 누구에게 어떤 문제가 있으며, 왜 지금 다루는지 설명한다. 1안·2안·3안을 비교하고 선택 이유를 남긴다.
- **실험:** 선택한 가설을 누구에게 어떻게 검증하고, 어떤 결과로 판정할지 정한다.
- **태스크:** 실험 아래에 소속되며, 담당자·상태·완료 기준을 각각 갖는다. 실험의 목적과 가설은 상위 실험 문서를 참조한다.
- **스프린트:** 이번 목표와 진행할 태스크를 연결하고, 마무리할 때 배운 점과 다음 작업을 기록한다.

## 폴더 구성

아래는 앞으로 문서를 추가할 때 따를 구조다. P001·E001·T001·S001과 제목은 예시이며, 실제 문제나 실험을 확정한 의미는 아니다. 폴더와 파일은 해당 작업을 시작할 때 만든다.

```text
chart-game-growth/
├── README.md
├── AGENTS.md
├── TASK-WRITING.md
├── .agents/skills/
│   └── problem-definition/
│       ├── SKILL.md                # 문제 정의 및 검토 절차
│       └── references/examples.md  # 문제 정의 사례
├── research/                       # 선정 배경, 서비스 정책, 데이터와 외부 사례
├── problems/
│   └── P001-시드구매-전환.md        # 문제 정의와 후보안 비교
├── experiments/
│   └── E001-유료가치-안내/
│       ├── README.md               # 실험 설계와 결과
│       └── tasks/
│           ├── T001-현황분석.md
│           ├── T002-화면기획.md
│           └── T003-개발전달.md
├── sprints/
│   ├── README.md                   # 스프린트 목록과 현재 스프린트 링크
│   └── S001.md                     # 이번 목표, 태스크 링크, 회고
├── request/
│   └── YYMMDD-태스크명.md          # 개발 전달용 상세 요구사항
└── docs/
    ├── 전략.md
    └── 문제-정의-가이드.md
```

문제 정의 스킬에는 사실과 추정의 구분, 대상 사용자와 상황의 구체화, 다른 원인 검토, 측정 기준, 가장 작은 검증 방법을 다룬다. 차트게임을 고른 이유와 바뀌는 정책·데이터는 `research/`에 기록하고 스킬에서 참조한다. 현재는 [문제 정의 가이드](docs/문제-정의-가이드.md)를 사용하며 스킬은 미작성 상태다.

## 문제 정의와 후보안 비교

문제 문서는 다음 순서로 작성한다.

1. **배경:** 왜 차트게임과 이 문제를 선택했는가. 사업 목표와 연결된 근거는 무엇인가.
2. **관찰한 사실:** 어떤 사용자에게 어떤 현상이 나타났는가. 출처·집계 기간·지표 정의는 무엇인가.
3. **문제 정의:** 사용자가 원하는 행동과 실제 행동 사이에 어떤 차이가 있는가.
4. **원인 가설:** 왜 발생한다고 보는가. 다른 설명은 무엇인가.
5. **후보안 비교:** 각 안의 원인 가설·해결방식·예상 영향·작업량·불확실성을 비교한다.
6. **선택과 이유:** 무엇을 먼저 검증하고, 다른 안은 왜 보류했는가. 연결된 실험은 무엇인가.

후보안은 같은 문제 문서 안에서 1안·2안·3안으로 비교한다. 구체적인 검증 설계를 진행하는 안부터 개별 실험 문서를 만든다. 보류한 대안도 선택 이유와 함께 보존한다.

## 개별 실험 문서

각 실험의 `README.md`에는 아래 내용을 작성한다.

| 항목 | 내용 |
|---|---|
| 상태 | 설계 중·실행 준비·진행 중·분석 중·종료·보류 |
| 연결된 문제와 후보안 | 문제 문서 링크와 선택한 안 |
| 문제 요약과 근거 | 대상 사용자의 문제와 확인한 사실 |
| 가설 | 무엇을 바꾸면 어떤 행동이 달라지고, 왜 시드 매출로 이어지는가 |
| 실험 설계 | 대상·제외 조건·변경 내용·대조군·배정 방법 |
| 측정과 판정 | 주 지표·보호 지표·기간·표본·성공 및 중단 기준 |
| 실행 태스크 | 해당 실험의 태스크 카드 링크 |
| 결과와 다음 결정 | 관찰 결과·불확실성·확대·수정·중단·판단 보류와 그 이유 |

실험 전 설계와 실험 후 결과를 같은 문서에 남긴다. 실행 이후 조건을 바꾸면 변경 시점과 이유를 기록하고, 최초 가설과 기준을 결과에 맞춰 덮어쓰지 않는다.

## 태스크 카드

태스크는 기본적으로 실험 하나에 소속시키고 `experiments/E번호-실험명/tasks/`에 저장한다. T번호는 저장소 전체에서 중복 없이 부여한다. 개발 전달용 요구사항은 기존 규칙대로 공통 `request/`에 두고 카드에서 연결한다.

```markdown
# T002 안내화면 기획

- 상위 실험: ../README.md
- 스프린트: 미배정
- 상태: 할 일
- 담당자: 미정
- 선행 태스크: 없음
- 요구사항: 미작성

## 목적

이 작업이 상위 실험의 어떤 부분을 해결하는지 작성한다.

## 작업 내용

- 실제로 수행할 작업을 작성한다.

## 완료 기준

- [ ] 결과를 확인할 수 있는 완료 조건을 작성한다.

## 산출물과 진행 기록

문서·Figma·요구사항·실제 구현 PR을 연결한다.
막힌 이유, 필요한 조치, 결정 내용을 기록한다.
```

태스크 상태는 **할 일 → 진행 중 → 검토 중 → 완료**를 기본으로 하고 **보류**를 별도로 둔다. 담당자와 일정은 합의한 내용만 확정한다.

## 스프린트 운영과 상태 관리

스프린트 문서에는 이번에 답할 질문, 연결된 문제·실험, 진행할 태스크 링크, 마무리 회고와 다음 작업을 적는다. 실험이 여러 스프린트에 걸쳐도 실험과 태스크 파일의 위치는 유지하고, 스프린트에서는 해당 카드를 연결한다.

| 관리 항목 | 원본 위치 |
|---|---|
| 문제와 후보안 비교 | 문제 문서 |
| 실험 가설·설계·결과·상태 | 실험 README |
| 태스크 담당자·상태·완료 기준 | 각 태스크 카드 |
| 스프린트 목표·작업 목록·회고 | 스프린트 문서 |
| 개발 상세 요구사항 | request 문서 |

스프린트와 실험의 작업 목록에는 카드 링크를 모으고 태스크 상태를 중복 작성하지 않는다. 여러 실험에 공통으로 필요한 작업은 기존 카드나 산출물을 연결하며 복제하지 않는다. 아직 특정 실험에 속하지 않는 초기 조사는 관련 문제 문서에서 정리하고, 해당 스프린트에서 진행할 작업을 연결한다.

태스크가 모두 완료돼도 실험은 관찰·분석·판정까지 마쳐야 종료한다. 후속 실험에서 추가 작업이 생기면 새 카드를 만들고 이전 결과를 연결한다. 코드 작업과 구현 PR은 알파스퀘어 조직 저장소에서 진행하며 이 저장소에는 관련 기획과 링크를 남긴다.
